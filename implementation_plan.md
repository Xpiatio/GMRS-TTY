# GMRS-TTY Staged Implementation Plan

## Stage 1: Foundation and PySide6 UI Skeleton
*   **Goal:** Establish the project layout, basic UI, and configuration management.
*   **Tasks:**
    *   Set up a Python virtual environment and `requirements.txt` (installing `PySide6`).
    *   Create the main dashboard layout: a header for personal info, a readonly text area for incoming messages (chat room), and an input line with a transmit button for outgoing messages.
    *   Create the JSON reading/writing module for the configuration page and populate the UI from `config.json` on boot.
    *   Implement the Contact Management dropdown and manual editing via a secondary window, saving to `contacts.json`.

## Stage 2: Piper TTS & Output Audio Engine (Simulation Mode)
*   **Goal:** Enable the app to speak the typed messages aloud using Piper.
*   **Tasks:**
    *   Create a local `/Voices` directory in the project root and download a few Piper ONNX voice models and their `.json` config files.
    *   Integrate the Piper Python module (or use Python's `subprocess` to call the Piper CLI directly). 
    *   Implement the GMRS formatting logic on outgoing text: prepend `[My Call] [My Name] calling [Target]` and use Python's `datetime` to handle the 15-minute FCC identification rule before appending the sign-off at the end of the message.
    *   Route the resulting audio stream generated by Piper to playback over the laptop speakers using a library like `sounddevice` or `pyaudio`.

## Stage 3: Offline STT & Input Audio Engine (Simulation Mode)
*   **Goal:** Listen to the laptop microphone and automatically transcribe it to the chat window.
*   **Tasks:**
    *   Install an STT binding like `vosk` (highly recommended for offline, low-latency live streaming) or `whisper`.
    *   Set up a continuous background audio stream utilizing `sounddevice` to capture microphone data.
    *   Since STT will be processing audio constantly, move the STT worker into a background `QThread`. Use Qt Signals/Slots to safely emit the transcribed text back to the main thread and append it to the chat UI without freezing the window.

## Stage 4: Refinement and State Management
*   **Goal:** Tighten the user experience and verify logic.
*   **Tasks:**
    *   Add auto-scrolling to the main chat view so new messages always appear at the bottom.
    *   Ensure the 15-minute callsign rule correctly resets its timer whenever a callsign is manually or automatically injected.
    *   Handle hardware selection gracefully (allow the user to pick which microphone and speaker to use from the configuration menu, rather than defaulting to system devices, which will be critical when hooking up real radios later).

## Stage 5: Hardware Hooks Readiness (Future-Proofing)
*   **Goal:** Prepare the software to step out of simulation mode and interact with real radios.
*   **Tasks:**
    *   Integrate `pyserial`.
    *   Wrap the TTS playback function in a sequence: Trigger PTT Serial pin -> Delay 300ms (for the radio to open up) -> Play Piper Audio -> Release PTT Serial pin.

## Stage 6: Off-Grid Model Bundling
*   **Goal:** Eliminate all runtime network dependencies so the application can run on a fresh, air-gapped install (per spec §5.1).
*   **Tasks:**
    *   Vendor the faster-whisper model files (e.g., `small.en` CTranslate2 artifacts: `model.bin`, `config.json`, `tokenizer.json`, `vocabulary.txt`) into a project `Models/STT/` directory. Update `WhisperModel(...)` to load from this local path instead of the default HuggingFace cache.
    *   Vendor the Silero VAD ONNX model into `Models/VAD/`. Replace `silero_vad.load_silero_vad()` with a direct `onnxruntime` load against the bundled file, and reimplement the streaming-iterator logic (or vendor just the `VADIterator` helper) so the `silero-vad` package's hidden first-run download is removed entirely.
    *   Audit all dependencies (`faster-whisper`, `silero-vad`, `noisereduce`, Piper) for any other lazy-fetch behavior. Confirm Piper voices remain entirely local (already in `Voices/`).
    *   Add a startup self-check that fails fast with a clear error if any required model file is missing — never silently attempt a download.
    *   Document the offline install procedure in `README.md`: how to obtain models, where to place them, and how to produce a `pip download`-based wheel cache for air-gapped installs.

## Stage 7: Cross-Platform Packaging & Distribution
*   **Goal:** Produce installable artifacts for Windows, Linux, and Raspberry Pi (per spec §5.2).
*   **Tasks:**
    *   Verify `sounddevice` / PortAudio works on Pi (ALSA), Linux desktop (PulseAudio / PipeWire), and Windows (WASAPI). Note device-enumeration quirks per platform in `README.md`.
    *   Resolve platform-specific Python dependency issues (PySide6 wheels on ARM64, CTranslate2 ARM wheels, ONNX Runtime ARM wheels). Pin versions in `requirements.txt` to known-good combinations.
    *   Benchmark STT latency on Raspberry Pi 4 / Pi 5 using bundled `small.en` int8. If unusable, fall back to `base.en` or `tiny.en` and expose the choice as a config option (`whisper_model` key in `config.json`).
    *   Package portable artifacts:
        *   Linux/Pi: tarball or `.deb` that bundles a Python venv, all wheels, and the `Models/` and `Voices/` directories.
        *   Windows: PyInstaller (or similar) one-folder distribution including the same bundled models.
    *   Verify each artifact runs on a freshly imaged machine with networking disabled.

## Stage 8: Dockerization (Multi-Architecture)
*   **Goal:** Ship a single multi-arch container image for reproducible deployment on x86_64 and Raspberry Pi (per spec §5.3).
*   **Tasks:**
    *   Write a `Dockerfile` based on a slim Python base (e.g., `python:3.13-slim`) that installs system packages needed for audio (PortAudio, ALSA dev libs, libsndfile), Qt platform plugins (`libxkbcommon`, `libxcb-*`, etc.), and any ONNX Runtime runtime deps.
    *   Bake the `Models/` and `Voices/` directories into the image so the container is self-sufficient on first run with no external mounts required.
    *   Build for `linux/amd64` and `linux/arm64` via `docker buildx`. Tag and publish as a single multi-arch manifest.
    *   Provide a `docker-compose.yml` (or documented `docker run` recipe) that wires:
        *   Audio I/O: PulseAudio socket mount (`/run/user/$UID/pulse`) or ALSA device passthrough (`--device /dev/snd`).
        *   Display: X11 socket mount (`/tmp/.X11-unix`) plus `DISPLAY` env, with a Wayland note for users on `wlroots`/GNOME.
        *   USB passthrough: `/dev/ttyUSB*` and USB sound cards for future radio integration.
        *   Persistent volumes: `config.json`, `contacts.json`, and the `Voices/` directory mounted from host so user state survives image upgrades.
    *   Verify air-gapped operation: run the image on a host with networking disabled and confirm full STT/TTS/UI functionality end-to-end.
